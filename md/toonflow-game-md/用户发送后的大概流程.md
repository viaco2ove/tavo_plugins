# 插件角度看待
## 用户发言后，这些插件是如何响应的？
谁去消费sendmsg， 记忆管理插件？内部有意图识别agent, 记忆管理agent?     
然后再去 编排插件？
编排插件内部再调用 事件agent 章节agent 记忆管理agent ?

## 插件在干嘛？
插件实际是tavo 事件回调推动的
例如：
_safeOn('chat:updated''input:beforeSend'
_safeOn('chat:updated'

event.cancel(); 可以完全拦截tavo 的事件，不然tavo 就会自己接着处理

## 插件优化
### 把章节判定 和事件进度 做到 编排插件
方案	做法	优点	缺点
A. 移到编排插件内	把 evaluateEventProgressByAi + evaluateChapterOutcomeByAi 复制/引用到 multi_character_stage，在编排前先判定章节 + 推进事件	所有编排逻辑集中一个插件	跟 event_manager 重复/冲突
B. 通过事件通信	编排前发一个 tf_story:check_chapter 事件，event_manager 监听并返回判定结果	解耦，不重复代码	需要改造 event_manager 支持回调

如果这样的话，意图识别和记忆管理也是编排的一部分了
【1】sentmsg->编排插件  事件通信【意图识别-是否需要记忆管理-章节判定-事件进度】-编排agent
->事件通信：发言插件-》反言agent ->语音合成播放  事件通信：编排插件
【2】开场白后->编排插件

### 插件是否可以互相调用
可以，方式有三种：

调用方式	示例	说明
window 共享接口	window.tmmIntent.refresh() (mcs→tmm)	暴露在 window 上的函数，直接调
tavo 事件系统	tavo.plugin.on('tf_story:check_chapter', fn)	监听/发送自定义事件
tavo 变量读写	tavo.set('tmm', state, 'chat')	通过变量传递数据
LLM 通道	window.tf_llm.callDirect(...)	插件统一用同一个 LLM 通道
